1. userId in JWT

Why userId was added

In Document 5, the React frontend decoded the JWT to get the userId:

// accountService.js (old approach)
export const getUserIdFromToken = (token) => {
    const payload = JSON.parse(atob(token.split('.')[1]))
    return payload.userId    // but userId was never actually IN the token!
}

The old token only contained the email as subject. To get the userId, you had two bad options:

  • Make an extra API call from the frontend: GET /api/users/byEmail?email=... (extra network roundtrip)
  • Put userId directly in the token as a custom claim (correct approach)

Adding userId as a JWT claim means the frontend can decode it locally — zero extra network calls, zero DB queries.

JWT custom claims explained

A JWT payload can carry any key-value pairs called claims. Standard claims are defined by the JWT spec (like sub, iat, exp). Custom claims are anything you add on top.

JWT Payload (before adding userId):
{
    "sub": "user@gmail.com",
    "iat": 1714000000,
    "exp": 1714086400
}

JWT Payload (after adding userId):
{
    "sub": "user@gmail.com",
    "userId": 1,             ← custom claim
    "iat": 1714000000,
    "exp": 1714086400
}
JWT is not encrypted — it is Base64 encoded. Anyone who has the token can decode and read the payload. Never put sensitive data (passwords, credit card numbers) in JWT claims. userId and email are safe to include.

Changes to user-service JwtUtil

generateToken — added userId parameter and claim

// BEFORE
public String generateToken(String email) {
    return Jwts.builder()
            .signWith(getSigningKey())
            .subject(email)
            .issuedAt(new Date())
            .expiration(new Date(System.currentTimeMillis() + expiration))
            .compact();
}

// AFTER
public String generateToken(String email, Integer userId) {
    return Jwts.builder()
            .signWith(getSigningKey())
            .subject(email)
            .claim("userId", userId)       ← adds custom claim to payload
            .issuedAt(new Date())
            .expiration(new Date(System.currentTimeMillis() + expiration))
            .compact();
}

.claim("userId", userId) adds any key-value pair to the JWT payload. The JJWT library serializes it into JSON and includes it in the signed token.

extractUserId — new method added

public Integer extractUserId(String token) {
    return getClaims(token).get("userId", Integer.class);
}

getClaims(token).get("userId", Integer.class) reads the userId key from the payload and casts it to Integer. The second argument Integer.class is a Class object — explained below.

Why Integer.class and not just Integer

The get() method signature is:

public <T> T get(String claimName, Class<T> requiredType)

It is a generic method. It needs the Class object at runtime to know what type to convert the value to. This is because Java generics use type erasure — at runtime, <T> becomes Object and the compiler's type information is gone. The only way to tell the method "I want an Integer" at runtime is to pass Integer.class explicitly.

What you writeWhat it isWhen it exists
IntegerA type — tells the compiler what variable can holdCompile time only — gone at runtime due to erasure
Integer.classA Class<Integer> object you can pass aroundRuntime — the method uses it to cast/convert the value
JDBC analogy: Similar to rs.getObject("col", Integer.class) in JDBC — you pass the class to tell the method what to convert the raw DB value into. Without it, you'd get back an Object and have to cast manually.

Changes to UserServiceImpl

The login() method already fetches the user object from the DB. The user.getId() is now passed to generateToken:

// BEFORE
return jwtUtil.generateToken(request.getMail());

// AFTER
return jwtUtil.generateToken(request.getMail(), user.getId());
// user object is already in scope from the findByMail() call above

Changes to api-gateway JwtUtil

The gateway validates tokens but never generates them. extractUserId was added so the gateway can (optionally) forward the userId to downstream services as a header in the future:

public Integer extractUserId(String token) {
    return getClaims(token).get("userId", Integer.class);
}

How the frontend uses it

In accountService.js, getUserIdFromToken now correctly reads the userId claim that is actually present in the token:

export const getUserIdFromToken = (token) => {
    const payload = JSON.parse(atob(token.split('.')[1]))
    return payload.userId    // ← userId claim is now actually in the token
}

The decode logic is unchanged. The fix was on the backend — putting userId into the token so this frontend code works correctly.

2. Docker Hardening

Kafka two-listener setup (9092 vs 9093) — bug fix

All three services had bootstrap-servers: localhost:9093 in their application.yaml files. This caused Kafka connection errors when running services locally (outside Docker).

The reason for two ports in docker-compose is intentional:

KAFKA_LISTENERS:           INTERNAL://0.0.0.0:9092, EXTERNAL://0.0.0.0:9093
KAFKA_ADVERTISED_LISTENERS: INTERNAL://kafka:9092,   EXTERNAL://localhost:9093
ListenerPortWho uses itWhen
INTERNAL9092Spring Boot services inside Dockerdocker-compose / K8s
EXTERNAL9093Host machine (IntelliJ, Postman)Local dev outside Docker

So localhost:9093 in application.yaml is correct for local development (host machine connecting to Dockerized Kafka via the EXTERNAL listener). When running inside Docker, the env var SPRING_KAFKA_BOOTSTRAP_SERVERS: kafka:9092 overrides it automatically.

Why both are needed: Inside Docker, localhost means the container itself — not the Kafka container. So Docker services use the INTERNAL listener at kafka:9092 (hostname = service name). Your host machine uses localhost:9093 which Docker maps to the EXTERNAL listener.

Multi-stage Dockerfiles

The original Dockerfiles were single-stage:

# OLD — single stage (requires pre-built JAR)
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY target/user-service-0.0.1-SNAPSHOT.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]

This required you to run mvn package manually before every docker build. If you forgot, Docker would fail or use a stale JAR.

The new Dockerfiles are multi-stage — Maven runs inside Docker:

# NEW — multi-stage (self-contained build)

# Stage 1: Build the JAR inside Docker
FROM maven:3.9-eclipse-temurin-21 AS builder
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline          ← download dependencies into a cached layer
COPY src ./src
RUN mvn package -DskipTests            ← compile and package

# Stage 2: Run only the JAR (no Maven, no source code — smaller image)
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=builder /app/target/user-service-0.0.1-SNAPSHOT.jar app.jar
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]

Why two stages?

StageBase imageSizePurpose
buildermaven:3.9-eclipse-temurin-21~500MBHas Maven + JDK to compile the project
finaleclipse-temurin:21-jre~180MBHas only JRE to run the JAR — much smaller

The final Docker image only contains the JRE + the JAR. The builder stage (with Maven, source code, etc.) is discarded. This keeps production images lean and secure.

Why pom.xml is copied first, before src/

Docker builds images in layers. Each instruction creates a new layer. Layers are cached — if nothing changed, Docker reuses the cached layer instead of re-running the step.

COPY pom.xml .                ← Layer A
RUN mvn dependency:go-offline ← Layer B (cached as long as pom.xml doesn't change)
COPY src ./src                ← Layer C
RUN mvn package -DskipTests  ← Layer D (only reruns if src/ or pom.xml changed)

If you only change code in src/, Docker reuses Layer B (the expensive dependency download). If you had copied everything at once (COPY . .), any code change would invalidate all layers and re-download all dependencies every time.

.dockerignore

Without .dockerignore, Docker sends your entire project folder to the build daemon as the "build context" — including target/ (compiled classes, ~50-100MB), .idea/, .git/ history, etc. This slows down every build even if those files are never used.

A .dockerignore file was created in each service folder with the same content:

target/
.idea/
*.iml
.git/
*.md
.mvn/
mvnw
mvnw.cmd
*.gitignore
*.gitattributes
EntryWhat it excludesWhy
target/Compiled classes, JARsLargest folder; Docker builds its own JAR in Stage 1
.idea/IntelliJ project filesIDE metadata — irrelevant to build
.git/Git historyCan be large; not needed in container
.mvn/, mvnw, mvnw.cmdMaven wrapperDocker uses its own Maven from the base image
Result: Docker build context is now just pom.xml + src/ — exactly what's needed and nothing more. Builds are faster and the daemon uses less memory.

JVM container memory flag

The ENTRYPOINT was updated in all Dockerfiles:

# BEFORE
ENTRYPOINT ["java", "-jar", "app.jar"]

# AFTER
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]

The problem without this flag: The JVM looks at the host machine's total RAM to size the heap. If your machine has 16GB but you give the container only 512MB, the JVM still tries to allocate a heap sized for 16GB. Docker sees the container exceeding its memory limit and kills it with OOMKilled (Out of Memory).

-XX:MaxRAMPercentage=75.0 tells the JVM: size the heap as 75% of the container's memory limit, not the host machine's total RAM. This flag is supported from Java 11 onwards and is the standard practice for running Java in containers.

ScenarioWithout flagWith flag
Container memory limit: 512MB, Host RAM: 16GBJVM allocates ~4GB heap → OOMKilled immediatelyJVM allocates ~384MB heap → runs within limit

docker-compose healthchecks

Before healthchecks, depends_on only waited for containers to start, not to be ready. MySQL takes ~20-30 seconds after container start to accept connections. Spring Boot services would start, fail to connect to MySQL, and crash. restart: on-failure was a workaround — healthchecks are the proper solution.

MySQL healthcheck

mysql:
  image: mysql:8.0
  ...
  healthcheck:
    test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
    interval: 10s    ← run this check every 10 seconds
    timeout: 5s      ← fail if no response within 5 seconds
    retries: 5       ← mark as unhealthy after 5 consecutive failures

mysqladmin ping is a MySQL command that returns OK when the MySQL server is ready to accept connections. Docker runs this command inside the container every 10 seconds.

Redis healthcheck

redis:
  image: redis:7.0
  ...
  healthcheck:
    test: ["CMD", "redis-cli", "ping"]
    interval: 10s
    timeout: 5s
    retries: 5

redis-cli ping sends a PING command to Redis. Redis responds with PONG when it is ready. Same pattern as MySQL — simple CLI command that confirms the service is accepting connections.

Kafka healthcheck

kafka:
  ...
  healthcheck:
    test: ["CMD", "kafka-broker-api-versions", "--bootstrap-server", "localhost:9092"]
    interval: 10s
    timeout: 10s     ← longer timeout because Kafka startup is slower
    retries: 5

kafka-broker-api-versions is a Kafka CLI tool that connects to the broker and asks for its API version list. If Kafka is not ready, this command fails. If it succeeds, Kafka is accepting connections.

depends_on with conditions

After adding healthchecks to infrastructure services, the Spring Boot service depends_on was updated to use condition: service_healthy instead of just listing the service name.

Old styleNew styleDifference
depends_on: - mysqldepends_on: mysql: condition: service_healthyOld: waits for container to start. New: waits for healthcheck to pass.
user-service:
  depends_on:
    mysql:
      condition: service_healthy    ← wait until mysqladmin ping succeeds
    redis:
      condition: service_healthy    ← wait until redis-cli ping succeeds
    kafka:
      condition: service_healthy    ← wait until kafka-broker-api-versions succeeds

For Spring Boot services (account-service, transaction-service, api-gateway) that depend on each other, condition: service_started is used instead of service_healthy because Spring Boot services don't have healthcheck commands defined. restart: on-failure handles retries for these.

Why not service_healthy for Spring Boot services? Adding a healthcheck to a Spring Boot service requires the spring-boot-starter-actuator dependency, which exposes a /actuator/health endpoint. This is a good future addition. For now, service_started + restart: on-failure achieves the same effect.

build: context

Previously docker-compose only referenced pre-built images (image: user-service:latest). Running docker-compose up would fail if the image didn't already exist — you had to manually run docker build for each service first.

Adding build: to each service tells Docker Compose to build the image automatically if it doesn't exist:

user-service:
  build: ./user-service      ← path to folder containing the Dockerfile
  image: user-service:latest ← tag to give the built image
  ...

Now docker-compose up --build builds all images from their Dockerfiles and starts everything in one command. The image: field is still kept so the built image gets a predictable name/tag for reuse.
